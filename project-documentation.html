1. Project Overview & Architecture

What is ShopFlow?

ShopFlow is a Spring Boot 3 e-commerce backend that demonstrates production-grade patterns:

  • Req 1: Concurrency control via Optimistic & Pessimistic locking (Strategy Pattern)
  • Req 2: Resource management via connection pools (HikariCP, Redis Lettuce, Thread Pools)
  • Req 3: Async event queue (Observer Pattern) for non-blocking invoice generation
  • Req 4: Batch processing for daily sales reports (chunked to avoid OOM)

JWT Architecture
Why JTI (JWT ID)? Each access token has a unique ID stored in the jti claim. When a user logs out, the JTI is stored in Redis with a TTL matching the token's remaining lifetime. On every request, the JwtAuthenticationFilter checks Redis to see if the token's JTI is blacklisted. This allows stateless JWT auth with the ability to revoke tokens before natural expiry.

4. Order Processing & Concurrency Control

Strategy Pattern for Locking

The system uses the Strategy Pattern to choose between two locking mechanisms depending on the purchase scenario:

+-------------------+ | PurchaseStrategy | (Interface) | + purchase(id, q) | +-------------------+ / \ / \ +------------------------+ +---------------------------+ | OptimisticPurchase | | PessimisticPurchase | | Strategy | | Strategy | +------------------------+ +---------------------------+ | - Uses @Version column | | - Uses SELECT ... FOR | | - No DB lock held | | UPDATE (exclusive lock) | | - Retry up to 3 times | | - Other threads WAIT | | - Best for normal | | - Best for flash sales | | purchases (low | | (high contention, | | contention) | | thousands competing) | +------------------------+ +---------------------------+
Optimistic Locking (Normal Purchases)
How it works: The products table has a version column. When JPA saves a product, it generates: UPDATE products SET stock_quantity=?, version=version+1 WHERE id=? AND version=?. If another thread already changed the version, the WHERE clause matches 0 rows, and Hibernate throws OptimisticLockException. The strategy retries up to 3 times. 
// Product entity - the @Version column is the key
@Version
private Long version = 0L;

// What happens under the hood:
Thread A: reads product (version=5, stock=100)
Thread B: reads product (version=5, stock=100)
Thread A: saves (stock=99) -> UPDATE ... WHERE version=5 -> SUCCESS, version becomes 6
Thread B: saves (stock=99) -> UPDATE ... WHERE version=5 -> 0 rows matched! EXCEPTION!
Thread B: retries -> reads (version=6, stock=99) -> saves (stock=98) -> SUCCESS
Pessimistic Locking (Flash Sales)
How it works: The repository uses @Lock(LockModeType.PESSIMISTIC_WRITE) which generates SELECT ... FOR UPDATE. This tells PostgreSQL to exclusively lock the row. Any other transaction trying to read the same row will block (wait) until the first transaction commits or rolls back. 
// FlashSaleRepository - the lock is declared here
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT f FROM FlashSale f WHERE f.id = :id")
Optional<FlashSale> findByIdWithLock(@Param("id") UUID id);

// What happens under the hood:
Thread A: SELECT ... FOR UPDATE -> gets lock, reads remaining=50
Thread B: SELECT ... FOR UPDATE -> BLOCKS (waits for Thread A)
Thread C: SELECT ... FOR UPDATE -> BLOCKS (waits)
Thread A: remaining=49, COMMIT -> lock released
Thread B: unblocks, reads remaining=49, sets 48, COMMIT
Thread C: unblocks, reads remaining=48, sets 47, COMMIT
// No retries needed - threads are serialized at DB level

5. Flash Sales

Flash Sale Lifecycle
ADMIN creates flash sale: POST /api/flash-sales { productId, discountedPrice, totalQuantity, startTime, endTime } -> Saves FlashSale entity with remainingQuantity = totalQuantity, active = true USERS purchase during flash sale: POST /api/orders/flash-sale { flashSaleId, quantity } -> OrderService.placeFlashSaleOrder() -> PessimisticPurchaseStrategy.purchase() 1. SELECT ... FOR UPDATE (locks the flash_sales row) 2. Check flash sale is still active 3. Check remaining_quantity >= requested quantity 4. Decrement remaining_quantity 5. If remaining_quantity == 0: set active = false (sold out!) 6. COMMIT (releases lock, next thread proceeds) -> Create Order + OrderItem -> Publish OrderPlacedEvent (async invoice generation) <-- 200 OK { order details }
Why pessimistic here? In a flash sale, thousands of users hit the same product simultaneously. Optimistic locking would cause massive retry storms (almost every thread conflicts). Pessimistic locking serializes access — only one thread at a time touches the stock, so there's zero wasted work.

7. Batch Processing & Reporting

Daily Sales Report Generation
Every day at 00:00 UTC (cron: "0 0 0 * * *") | v DailySalesJob.runDailyReport() [runs in batchExecutor thread pool] | v DailySalesReportService.generateReportForDate(yesterday) | |-- Check if report already exists (idempotent) |-- Create report entity with status=PROCESSING | |-- CHUNK LOOP (page size = 500): | | | |-- Page 0: fetch orders 1-500 from yesterday | | +-- sum revenue, count orders | | | |-- Page 1: fetch orders 501-1000 | | +-- sum revenue, count orders | | | |-- Page 2: fetch orders 1001-1500 | | +-- sum revenue, count orders | | | +-- ... until no more pages | |-- Update report: totalOrders, totalRevenue, processedAt |-- Set status = COMPLETED | v Done (if exception: status = FAILED)
Why chunking? If you had 1 million orders yesterday and loaded them all into memory at once, you'd get an OutOfMemoryError. By fetching 500 at a time (using Spring Data's Pageable), you keep memory usage constant regardless of data volume.

8. Resource Management (Connection Pools)

Why Connection Pools?
Problem without pools: Every HTTP request needs a database connection. Creating a new TCP connection to PostgreSQL takes ~5-10ms. Under 1000 concurrent requests, you'd create 1000 connections, overwhelming the DB and wasting time on connection setup.

Solution: Keep a pool of pre-created connections. Threads borrow a connection, use it, return it. Connection creation happens once at startup, not per-request.

Orders/sec: 1-5    -> 5 core threads handle it, queue stays empty

AsyncConfig.java - Thread Pool Definitions

@Configuration  // Marks this class as a source of bean definitions
@EnableAsync     // (redundant with main class, but makes config self-documenting)
@EnableScheduling
public class AsyncConfig {

    @Bean(name = "orderExecutor")  // Registers this executor in Spring's context
                                     // @Async("orderExecutor") references this name
    public Executor orderExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);        // 5 threads always alive
        executor.setMaxPoolSize(20);        // up to 20 under pressure
        executor.setQueueCapacity(100);     // 100 tasks can wait in line
        executor.setThreadNamePrefix("order-async-");  // visible in logs: "order-async-1"
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy());
            // When everything is full (20 threads + 100 queue):
            // Instead of throwing RejectedExecutionException,
            // the CALLING thread (Tomcat HTTP thread) runs the task.
            // This creates backpressure: HTTP responses slow down,
            // which naturally throttles incoming requests.
        executor.initialize();  // Creates the internal thread pool
        return executor;
    }

    @Bean(name = "batchExecutor")  // Separate pool for batch jobs
    public Executor batchExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(2);       // Only 2 core — batch jobs are rare
        executor.setMaxPoolSize(5);        // Max 5 — don't starve DB connections
        executor.setQueueCapacity(10);     // Small queue — batch jobs are few
        executor.setThreadNamePrefix("batch-job-");
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}

OptimisticPurchaseStrategy.java - Retry Loop

@Component("optimisticPurchase")  // Spring bean with qualifier name
public class OptimisticPurchaseStrategy implements PurchaseStrategy {

    private static final int MAX_RETRIES = 3;  // Give up after 3 conflicts

    @Override
    @Transactional  // Each attempt runs in its own transaction
    public Product purchase(UUID productId, int quantity) {
        int attempt = 0;
        while (attempt < MAX_RETRIES) {
            try {
                return attemptPurchase(productId, quantity);
            } catch (ObjectOptimisticLockingFailureException ex) {
                // Another thread modified the product between our READ and SAVE
                // The @Version check failed: WHERE version=X matched 0 rows
                attempt++;
                if (attempt >= MAX_RETRIES) {
                    throw new RuntimeException("Product is being updated...");
                }
                // Otherwise: loop again, re-read fresh data, try again
            }
        }
    }

    private Product attemptPurchase(UUID productId, int quantity) {
        Product product = productRepository.findById(productId)  // SELECT * FROM products WHERE id=?
                .orElseThrow(...);

        if (product.getStockQuantity() < quantity) {
            throw new RuntimeException("Insufficient stock");
        }

        product.setStockQuantity(product.getStockQuantity() - quantity);
        return productRepository.save(product);
        // JPA generates:
        // UPDATE products SET stock_quantity=?, version=version+1
        // WHERE id=? AND version=?
        // If version changed -> 0 rows updated -> OptimisticLockException
    }
}

OrderEventListener.java - Async Observer

@Component
public class OrderEventListener {

    private final InvoiceService invoiceService;

    @Async("orderExecutor")  // THIS IS THE KEY LINE
    // Without @Async: this method runs in the SAME thread as the HTTP request
    // With @Async: Spring intercepts the call, submits it to "orderExecutor"
    // pool, and returns immediately. The HTTP response goes out before
    // this method even starts executing.
    @EventListener  // Spring calls this whenever OrderPlacedEvent is published
    public void onOrderPlaced(OrderPlacedEvent event) {
        Order order = event.getOrder();
        // This runs in thread "order-async-3" (or similar)
        // The original HTTP thread already sent 200 OK to the user

        invoiceService.generateInvoice(order);
        // If this fails, the order is STILL confirmed
        // Invoice generation is best-effort, logged for manual retry
    }
}

DailySalesReportService.java - Batch Chunking

private static final int CHUNK_SIZE = 500;  // Process 500 orders per DB query

@Transactional
public void generateReportForDate(LocalDate date) {
    // Idempotency: if report exists, skip (safe to re-run)
    if (reportRepository.existsByReportDate(date)) return;

    // Create report in PROCESSING state (visible in DB even if job crashes)
    DailySalesReport report = DailySalesReport.builder()
            .reportDate(date)
            .status(ReportStatus.PROCESSING)
            .build();
    report = reportRepository.save(report);

    // Time range: full day in UTC
    Instant from = date.atStartOfDay(ZoneOffset.UTC).toInstant();
    Instant to = date.plusDays(1).atStartOfDay(ZoneOffset.UTC).toInstant();

    int page = 0;
    int totalOrders = 0;
    BigDecimal totalRevenue = BigDecimal.ZERO;
    Page<Order> chunk;

    do {
        // Fetch only CHUNK_SIZE orders at a time
        // SQL: SELECT * FROM orders WHERE status='CONFIRMED'
        //      AND created_at BETWEEN ? AND ? LIMIT 500 OFFSET ?
        chunk = orderRepository.findByStatusAndCreatedAtBetween(
                OrderStatus.CONFIRMED, from, to,
                PageRequest.of(page, CHUNK_SIZE));

        // Process this chunk in memory (max 500 objects)
        for (Order order : chunk.getContent()) {
            totalRevenue = totalRevenue.add(order.getTotalAmount());
        }
        totalOrders += chunk.getContent().size();
        page++;

    } while (chunk.hasNext());  // hasNext()=false when last page

    // Persist final results
    report.setTotalOrders(totalOrders);
    report.setTotalRevenue(totalRevenue);
    report.setStatus(ReportStatus.COMPLETED);
    reportRepository.save(report);
}

TokenBlacklistService.java - Redis Usage

@Service
public class TokenBlacklistService {

    private final StringRedisTemplate redisTemplate;
    // StringRedisTemplate is Spring's Redis client
    // It uses the Lettuce connection pool configured in application.yml

    private static final String BLACKLIST_PREFIX = "jwt:blacklist:";

    public void blacklist(String jti, long remainingMs) {
        // Store in Redis: key="jwt:blacklist:abc-123", value="1"
        // TTL = remaining token lifetime (e.g., 8 minutes left)
        // After TTL expires, Redis auto-deletes the key
        // (no point keeping it — the JWT itself has also expired by then)
        String key = BLACKLIST_PREFIX + jti;
        redisTemplate.opsForValue().set(key, "1", Duration.ofMillis(remainingMs));
    }

    public boolean isBlacklisted(String jti) {
        // Called on EVERY authenticated request by JwtAuthenticationFilter
        // Redis lookup: O(1), ~0.1ms — extremely fast
        // Returns true if the key exists (token was revoked)
        return redisTemplate.hasKey(BLACKLIST_PREFIX + jti);
    }
}

JwtAuthenticationFilter.java - Request Pipeline

@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    // OncePerRequestFilter = guaranteed to run exactly once per HTTP request
    // (even if request is forwarded internally)

    @Override
    protected void doFilterInternal(request, response, filterChain) {

        String jwt = extractTokenFromRequest(request);
        // Extracts "Bearer xxx" from Authorization header, returns "xxx"

        if (StringUtils.hasText(jwt)          // 1. Token exists
            && jwtService.validateToken(jwt)   // 2. Signature valid, not expired
            && jwtService.isAccessToken(jwt)   // 3. It's an access token (not MFA)
            && !tokenBlacklistService.isBlacklisted(jwtService.getJtiFromToken(jwt)))
            // 4. Not in Redis blacklist (not logged out)
        {
            String email = jwtService.getEmailFromToken(jwt);
            UserDetails userDetails = userDetailsService.loadUserByUsername(email);
            // Loads user + roles from DB

            UsernamePasswordAuthenticationToken authentication =
                new UsernamePasswordAuthenticationToken(
                    userDetails, null, userDetails.getAuthorities());
            // Creates an Authentication object with user's roles

            SecurityContextHolder.getContext().setAuthentication(authentication);
            // Sets the current user in Spring Security's context
            // Now @AuthenticationPrincipal works in controllers
            // And @PreAuthorize("hasRole('ADMIN')") can check roles
        }

        filterChain.doFilter(request, response);
        // ALWAYS continue the filter chain — even if auth failed
        // (Spring Security handles 401 via exceptionHandling config)
    }
}

.anyRequest().authenticated()  // Everything else needs a valid JWT

// Password encoder:
new BCryptPasswordEncoder(12)  // Strength 12 = 2^12 = 4096 hash rounds

application.yml - Configuration Explained

# DATABASE
datasource:
  url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:6000}/authdb
  # ${VAR:default} syntax: use env var if set, otherwise use default
  # Connects to PostgreSQL on port 6000, database named "authdb"

  hikari:
    maximum-pool-size: 10   # Max 10 threads can query DB at once
    minimum-idle: 5         # 5 connections pre-warmed (no startup delay)
    connection-timeout: 30000  # 30s - if pool is full, wait up to 30s
    max-lifetime: 1800000   # 30min - recycle before DB's own timeout kills it
    leak-detection-threshold: 60000  # Warn if code holds connection > 60s
    # This catches bugs like: forgot to close transaction, infinite loop in service

# JPA / HIBERNATE
jpa:
  hibernate:
    ddl-auto: update    # Auto-create/alter tables to match entities
    # WARNING: in production use "validate" + Flyway migrations
  open-in-view: false   # IMPORTANT: prevents lazy loading in controllers
    # If true: DB connection held for entire HTTP request (wasteful)
    # If false: must eagerly fetch all data in service layer

# REDIS (for JWT blacklisting)
data:
  redis:
    lettuce:
      pool:
        max-active: 10   # Only 10 connections to Redis at once
        min-idle: 2      # 2 always warm (blacklist checks are frequent)
        max-wait: 2000ms # Fail fast if Redis is overloaded

# JWT CONFIG
app:
  jwt:
    access-token-expiration-ms: 900000  # 15min - short-lived for security
    refresh-token-expiration-days: 7    # 7 days - long-lived, stored in DB
    # Why short access tokens? If stolen, attacker has max 15min window
    # Refresh tokens are in HttpOnly cookies (can't be stolen by XSS)

Summary: How Everything Connects

USER JOURNEY (placing a normal order): 1. REGISTER: POST /api/auth/register -> Password hashed (BCrypt), saved to 'users' table -> Verification email sent ASYNC (doesn't block response) 2. VERIFY: GET /api/auth/verify-email?token=xxx -> Token looked up in 'email_verification_tokens' -> User marked as verified 3. LOGIN: POST /api/auth/login -> Credentials checked, JWT access token generated -> Refresh token hashed and stored in 'refresh_tokens' -> Access token returned, refresh token in HttpOnly cookie 4. BROWSE: GET /api/products (public, no auth needed) -> Returns product list from 'products' table 5. ORDER: POST /api/orders (requires auth) -> JwtAuthenticationFilter validates token on EVERY request -> Checks Redis blacklist (is token revoked?) -> OrderService uses OptimisticPurchaseStrategy -> Decrements stock (with @Version conflict detection) -> Saves order to 'orders' + 'order_items' -> Publishes OrderPlacedEvent -> Returns 200 OK immediately 6. ASYNC (in orderExecutor thread, user doesn't wait): -> OrderEventListener receives event -> InvoiceService generates invoice -> Saved to 'invoices' table 7. NIGHTLY (in batchExecutor thread, midnight UTC): -> DailySalesJob triggers -> Processes yesterday's orders in 500-row chunks -> Saves aggregate to 'daily_sales_reports' 8. CLEANUP (every hour): -> TokenCleanupScheduler deletes expired/revoked refresh tokens -> Keeps 'refresh_tokens' table clean
